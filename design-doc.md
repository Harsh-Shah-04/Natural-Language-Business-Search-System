## Problem Statement

Build a web app where businesses register via a form, get converted into vector embeddings, and can be found through natural-language search instead of keyword matching — e.g. "GST Expert" should surface a "Chartered Accountant," and "someone who can help restaurants with packaging" should surface "Food Packaging" companies, without those exact words appearing in the query. Evaluated on: embeddings, vector databases, semantic search, NLP, ranking, full-stack execution.

## Dataset (inspected directly)

`Business_Matchmaking_Test_Dataset_V2_120_Companies.xlsx` — 120 rows, 14 columns:
`Business Name, Nature, Industry, Sub Category, City, State, Contact Person, Email, Website, Phone, Business Description, Products/Services, Keywords, Specialties`.

`Business Description`, `Products/Services`, `Keywords`, and `Specialties` are the semantically rich free-text fields — these are what get embedded. `Industry`, `Sub Category`, `City`, `State` are structured metadata — these become filters/boosts, not embedding input (mixing them into the embedded text would dilute the vector with low-entropy category labels that repeat across dozens of rows).

## Constraints

- Embeddings must be free/local (open-weight model via HuggingFace/sentence-transformers) — no OpenAI/Voyage API budget.
- Must run locally for the reviewer; live deployment is a stretch goal if time allows, not a requirement.
- Timeline: a few days — enough to do this properly (hybrid search + explicit ranking stage + clean ingestion + polished UI), not enough to over-build.
- Tech stack is partially fixed by the assignment: React frontend, MongoDB as the database, one of {MongoDB Atlas Vector Search, pgvector, Qdrant, Pinecone} as the vector layer, backend in Node or FastAPI.

## Premises (agreed)

1. Vector-only search will fail the assignment's own example queries on literal/near-literal terms — hybrid search (keyword + vector) is required, not optional.
2. "Ranking" is a named evaluation criterion. Returning raw cosine-similarity top-k is the naive baseline, not the answer — an explicit ranking/fusion stage is required.
3. 120 rows is small. The architecture must be correct at this scale without pretending it needs to survive 10M vectors — and must say explicitly what would change if it did.
4. Free/local embeddings rule out OpenAI/Voyage; the model must be open-weight and CPU-runnable.
5. New businesses added via the UI must be embedded synchronously (or near-synchronously) on creation — not batched — so they're immediately searchable.

## Approaches Considered

### Approach A: MongoDB Atlas Vector Search (single-store)
One MongoDB Atlas cluster (free M0 tier) holds business records, embeddings, and a full-text search index together. Hybrid search = one `$search` (keyword/Lucene) query + one `$vectorSearch` query, fused via Reciprocal Rank Fusion (or Atlas's native `$rankFusion` aggregation stage), then an optional cross-encoder rerank on the fused top-20.
- Effort: M (human ~2-3 days) · Risk: Low
- Pros: matches the assignment's stated database exactly; no second data store, no sync pipeline, no dual-write failure mode; free tier needs no credit card and the same connection string works for local dev and a deployed backend.
- Cons: Atlas is cloud-hosted, so "local" still needs internet connectivity; defining the Atlas Search index (JSON schema) is a small new concept versus a plain collection.

### Approach B: MongoDB (system of record) + self-hosted Qdrant (dedicated vector engine)
MongoDB holds business records as source of truth; a local Qdrant Docker container holds embeddings + filterable payload, keyed by MongoDB's `_id`. Every write becomes a two-step: insert to Mongo, then upsert to Qdrant.
- Effort: L (human ~4-5 days) · Risk: Med (dual-write consistency is a real, if largely theoretical at this scale, design question)
- Pros: textbook production pattern (system-of-record DB in front of a dedicated search engine); fully offline; gives concrete talking points (HNSW, payload filtering) for a systems-design follow-up.
- Cons: two data stores to run and keep consistent for 120 rows; more processes to explain and demo; spends limited time on a consistency problem this dataset doesn't actually have.

### Approach C: MongoDB (storage only) + in-process vector index (FAISS/NumPy, no vector DB service)
Embeddings load into a NumPy matrix / FAISS `IndexFlatIP` in the FastAPI process at startup (120 × 384 floats ≈ 180KB). Brute-force cosine similarity per query; index updated in-memory on new business creation.
- Effort: S (human ~1-2 days) · Risk: Low technically, Medium on interview-scoring risk
- Pros: fastest to build, zero extra services, nothing to break during a live demo; demonstrates judgment about not over-provisioning infrastructure.
- Cons: "vector databases" is explicitly named in the assignment's own evaluation checklist — skipping a real one reads as not engaging with that requirement; weak answer to the likely "what changes at 50k businesses?" interview follow-up, since you'd be describing a migration instead of having built the real thing.

## Recommended Approach

**A: MongoDB Atlas Vector Search.** It is the only option that satisfies every stated constraint simultaneously: it uses the exact required database, directly demonstrates real vector-database skill (the thing being graded), needs no extra services beyond your own app, and behaves identically in local dev and a deployed environment. Approach B is the more textbook-impressive answer but spends the limited time budget on a consistency problem a 120-row dataset doesn't create. Approach C is fastest but undercuts the assignment's own grading criteria.

Revised effort estimate: **3-5 days**, not 2-3 — Atlas index setup/debugging, ingestion, the hybrid+RRF+rerank pipeline, CRUD with validation, two React pages, and a hand-labeled golden eval set add up. See "Sequencing under time pressure" below for what to build first if time runs short.

### System design

**Embedding model:** `BAAI/bge-small-en-v1.5` via `sentence-transformers`, 384 dimensions, CPU inference (~10-30ms per short text). Chosen over `intfloat/e5-small-v2` for simplicity — bge-small doesn't require the `query:`/`passage:` prefix convention e5 needs to hit its benchmark numbers, removing a whole class of "forgot the prefix, quality silently degraded" bugs, at comparable MTEB retrieval quality. Run the model in the FastAPI process itself (not a separate microservice) — one language, one process, no inference-serving infra to build for a free/local model.

**Embedding text construction:** for each business, concatenate `Business Description + Products/Services + Keywords + Specialties + Sub Category` into one string before embedding. Contact fields (name/email/phone/website) are excluded — they carry no semantic signal and would just add noise.

**Storage & indexing:** default to two Atlas indexes on the `businesses` collection — a `vectorSearch`-type index on `embedding` (384 dims, cosine similarity) and a `search`-type (Lucene) index on the four text fields. Both point at the same collection, so there's no sync lag between them even as two definitions. Whether Atlas's newer unified index definitions let these collapse into one is exactly what "The Assignment" (below) validates first — treat it as a nice-to-have simplification to confirm, not a foundational assumption the rest of the design depends on.

**Ranking pipeline** (this is what actually answers the "Ranking" evaluation criterion):
1. Embed the incoming query with the same model.
2. Run `$vectorSearch` (top ~30 by cosine similarity) and Atlas `$search` (top ~30 by Lucene BM25-style relevance) in parallel against the same collection. Filters apply differently per stage: `$vectorSearch` takes City/Industry as a `filter` clause evaluated before the ANN search (pre-filter); `$search` takes them as a `compound.filter` clause. Both need the filtered fields indexed as filterable in their respective index definitions.
3. Fuse the two ranked lists with Reciprocal Rank Fusion (`score = Σ 1/(60 + rank)` per list) into a single top-20.
4. Rerank the fused top-20 with a small local cross-encoder (`cross-encoder/ms-marco-MiniLM-L-6-v2`) scoring (query, business_description) pairs directly — cheap at 20 pairs, and this two-stage retrieve-then-rerank shape is current best practice for exactly this reason: bi-encoder embeddings are fast but coarse, cross-encoders are precise but too slow to run over the whole corpus. Target end-to-end pipeline latency: <500ms p50 on a laptop CPU (two Atlas round-trips + local rerank of 20 pairs) — worth timing early since it's the one number worth having in your back pocket for a live demo.
5. Return top-10 with a lightweight "matched via: semantic / keyword / both" tag per result — cheap to compute from step 2's membership, and it turns an opaque ranked list into something the UI can visibly explain, which is itself a good interview talking point about search UX. Empty results (query matches nothing above a minimal relevance floor) return an explicit empty array, not an error — the UI should show a "no matches, try broadening your search" state rather than a blank screen.

**Sequencing under time pressure:** hybrid search (steps 1-3) is the core deliverable and must work first. Cross-encoder reranking (step 4) and the golden-query eval harness are the second layer — build and validate hybrid search end-to-end before adding either, so there's always a working, gradable system even if the stretch pieces don't land in time.

**Ingestion:** a `scripts/seed.py` reads the provided `.xlsx`, builds the embedding text per row, embeds in a batch, and bulk-upserts into MongoDB — idempotent on `Business Name` so it's safe to re-run. New businesses via the UI hit `POST /api/businesses`, which validates, embeds synchronously, and inserts — same collection, so it's searchable as soon as Atlas's index catches up (near-real-time, typically sub-second, not instant — see caveat below).

**API surface:** `POST /api/businesses` (create — Pydantic schema requiring at minimum Business Name + one of Description/Products/Services/Keywords, since an empty string has nothing meaningful to embed; rejects with 422 on missing required fields; enforces a unique index on `Business Name` and returns 409 on duplicate, matching the seed script's own idempotency key), `GET /api/businesses` (browse/paginate), `GET /api/businesses/:id`, `POST /api/search` (the ranking pipeline above, request `{query, filters?, limit?}`, returns `{results: [...]}` with an empty array — not an error — when nothing matches).

**Near-real-time indexing caveat:** Atlas Search/Vector Search indexes update asynchronously after a write, typically within a second but not guaranteed-instant. This mostly matters for the live demo: after registering a business through the UI, show it immediately in a "your registered businesses" list (a plain `GET`, no index involved) so the reviewer sees confirmation right away, even if the very next semantic search lags by a beat.

**Frontend (React):** a search page (query box + optional city/industry filter + result cards showing name, description snippet, and the match-reason tag) and a registration page (form mirroring the dataset schema) posting to `POST /api/businesses`.

### What changes at scale (addresses Premise 3 directly)

At 120 rows, none of this is a performance concern — brute-force would even work. Written down so it doesn't need to be re-derived under interview pressure: at 10k-100k businesses, Atlas Vector Search's HNSW indexing already scales without architecture changes; ingestion would move from row-by-row upsert to `bulkWrite` batches; new-business embedding would move off the request path into a background queue so registration latency doesn't grow with embedding cost; and query-embedding results would get a small LRU cache since real query distributions are heavily repeated.

### Evaluation plan

Build a ~15-query golden set derived from the dataset's own `Sub Category` diversity (mirroring the assignment's own examples — "GST Expert" → Chartered Accountant/Tax Consultant/Indirect Tax Advisor rows, "restaurant packaging help" → Food Packaging rows), with expected matching business IDs per query. Measure precision@5 vector-only vs. hybrid+rerank. This turns "ranking works" from an assertion into evidence you can show in the README — the single highest-leverage thing you can add given the assignment explicitly names ranking as a graded skill.

## Open Questions

- Should city/industry filters be explicit UI dropdowns, or extracted from the natural-language query itself (e.g. detecting "in Mumbai" or "restaurant" via a closed-world gazetteer built from the dataset's own City/Industry values)? Recommend: explicit dropdowns for the core build; NL filter extraction as a stretch feature if time allows — it's a nice NLP touch but not required to pass the assignment's stated examples.
- Whether to add authentication for business registration. The assignment doesn't ask for it; recommend leaving it open (anyone can register) to stay in scope, and noting the omission explicitly in the README as a deliberate scope decision.

## Success Criteria

- All 120 businesses from the provided dataset are imported and searchable.
- A business added through the UI is searchable in the very next query, no restart or batch job needed.
- The assignment's own example queries ("GST Expert," "restaurant packaging help") return the semantically correct businesses in the top 5.
- The golden-query eval shows hybrid+rerank measurably outperforming vector-only search (not just claimed).
- A fresh clone runs end-to-end (seed script → search working) in under 10 minutes following the README.
