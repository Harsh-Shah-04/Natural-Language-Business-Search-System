## What changed from V1

V1 presented each architecture choice as simply correct. V2's job — per a search-grounded Step 0 challenge and an independent outside-voice pass — is to make the doc's reasoning survive interrogation, not just its conclusions. Nothing in the underlying tech stack changed. What changed:

1. **Owns the scale tension instead of hiding it.** A vector database is not technically necessary at 120 rows (see below). V1 stated Atlas Vector Search as simply "the right choice"; V2 states it's used *despite* not being strictly necessary, because it's zero marginal cost given MongoDB is already required and it directly satisfies the assignment's own "vector databases" grading line.
2. **Cross-encoder reranking is evidence-gated, not assumed.** Kept only if a golden-query eval shows it measurably helps.
3. **`filters` param is an allow-list, not free-form pass-through** — closes a NoSQL-injection-shaped gap, and the allow-list is derived from live DB values (cached), not a static seed-time snapshot, so newly registered businesses stay filterable.
4. **Both local models (embedder + reranker) background-warm-up after process start**, with independent health checks — the API is reachable instantly and neither model's load failure takes down unrelated endpoints, and neither eats a live user's first request.
5. **Golden eval set expanded to ~30-40 queries** — 15 queries didn't have enough statistical resolution to reliably detect whether reranking helps.
6. **RRF's k=60 is explicitly labeled a standard default, not scale-tuned** — honest framing costs nothing; pretending it was re-derived for this dataset size would have been the same "asserted, not owned" pattern flagged elsewhere.
7. **Verified, not assumed:** direct inspection of the dataset confirms all 120 `Business Name` values are unique — the unique-index design decision is safe, confirmed against real data rather than assumed.

## System Design (V2)

**Storage & indexing:** default to two Atlas indexes — a `vectorSearch`-type index on `embedding` (384 dims, cosine similarity) and a `search`-type (Lucene) index on the four text fields. Whether Atlas's newer unified index definitions let these collapse into one is validated in the Day-1 spike below, not assumed.

**Embedding text construction:** `Business Description + Products/Services + Keywords + Specialties + Sub Category`, concatenated per business. Contact fields excluded (no semantic signal).

**Model loading:** both the embedder (`BAAI/bge-small-en-v1.5`) and the reranker (`cross-encoder/ms-marco-MiniLM-L-6-v2`, if it survives the eval gate) begin loading in a background thread immediately on process start. The API is reachable instantly. `/health/api` reports the API is up independent of `/health/model`, which reports each model's individual load state. No live request ever eats a cold model-load.

**`POST /api/businesses`:** Pydantic schema requiring Business Name + at least one of Description/Products/Services/Keywords; 422 on missing fields; unique index on Business Name (verified safe — all 120 seed rows are unique) returning 409 on duplicate.

**`POST /api/search`:** `{query, filters?, limit?}`.
1. Embed the query.
2. Run `$vectorSearch` (top ~30) and Atlas `$search` (top ~30) in parallel. `filters.city` / `filters.industry` are validated against an allow-list of *actual current values* pulled from the live database (queried at startup, cached, invalidated on new-business creation) — not a static seed-time snapshot, so newly registered businesses stay filterable. Any value outside the allow-list returns 422, not a pass-through query clause — closes the injection surface.
3. Fuse with Reciprocal Rank Fusion, `score = Σ 1/(60 + rank)`. k=60 is the standard IR-literature default, used as-is and labeled as such — not re-derived for this corpus size, and the doc says so rather than implying otherwise.
4. If reranking passed its eval gate (see below): rerank the fused top-20 with the cross-encoder. Target end-to-end latency: <500ms p50.
5. Return top-10 with a "matched via: semantic / keyword / both" tag. Empty results return `[]`, not an error.

**Evaluation plan:** ~30-40 hand-labeled queries derived from the dataset's own Sub Category/Industry diversity (up from V1's 15 — enough queries that a single flip doesn't dominate the precision@5 signal). Measure precision@5 vector-only vs. hybrid vs. hybrid+rerank. **Reranking ships only if it measurably improves precision@5 on this set.** This is the actual evidence behind "ranking works," not an assertion.

**What changes at scale:** unchanged from V1 — Atlas Vector Search's HNSW indexing already scales without architecture changes at 10k-100k businesses; ingestion moves to `bulkWrite` batches; new-business embedding moves off the request path into a background queue.

## NOT in scope

- **Authentication on business registration** — the assignment doesn't ask for it; anyone can register. Deliberate, documented scope decision, not an oversight.
- **Automated test implementation** — the test-coverage-target diagram (below) specifies what needs testing and why; writing the actual test suite is implementation work, not architecture. Flagging this explicitly because the outside-voice review noted the doc's depth on ranking design outweighed its depth on frontend/testing — the coverage diagram is the fix for that imbalance at the design-doc level; the code itself is next-phase work.
- **RRF k sensitivity sweep** — considered (outside voice raised it) and explicitly declined in favor of honest labeling over false precision; revisit only if the eval harness shows fusion quality is a bottleneck.
- **NL-based filter extraction** (e.g. detecting "in Mumbai" from free text) — explicit UI dropdowns cover the assignment's stated requirements; NL extraction is a stretch feature only if time remains.

## Failure Modes

| Codepath | Realistic failure | Test? | Error handling? | User sees |
|---|---|---|---|---|
| Model load (embedder/reranker) | OOM or missing weights on a constrained laptop | TARGET | Yes — background load, isolated health check | API works; search degrades with a clear "search temporarily unavailable" state, not a crash |
| `POST /api/search` filters | Caller sends a city/industry not in the live allow-list | TARGET | Yes — 422 | Clear validation error, not a silent empty result or an injected query |
| Atlas index update lag | New business searched immediately after registration, before near-real-time index catch-up | TARGET | Partial — registered-businesses list (plain GET) confirms creation instantly even if search lags a beat | No silent "it didn't work," registration is confirmed separately from searchability |
| Duplicate registration | Two UI submissions of the same Business Name (double-click) | TARGET | Yes — unique index, 409 | Clear "already registered" message, not a duplicate silent insert |

No critical gap (untested + unhandled + silent) identified — every failure mode above has at least a planned test and defined handling.
