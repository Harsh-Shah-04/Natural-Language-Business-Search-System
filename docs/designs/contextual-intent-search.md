## Problem Statement

The current system ranks well when the user's phrasing sits near the service
vocabulary in embedding space. It does not understand a user who describes a
**situation** and never names a service.

Reviewer's example:

> "My company keeps getting suspicious emails and I want someone to make sure
> our employees don't fall for scams."

Correct answer: the three Cybersecurity businesses. Their profiles say `SOC`,
`penetration testing`, `ISO27001`. The query says `company`, `emails`,
`employees`, `scams`. Zero overlap, lexical or semantic. Getting from symptom
to service requires world knowledge, which a 384-dim bi-encoder trained on
generic web text does not reliably supply, and which the cross-encoder cannot
supply either because it can only reorder what retrieval already surfaced.

Two distinct gaps, both real:

1. **No query understanding stage.** `search_businesses()` embeds the raw user
   string and searches. Nothing ever asks "what is this person actually trying
   to solve?"
2. **No visible reasoning.** A user types a paragraph and gets a ranked list.
   Nothing on screen says what the system understood. Correct ranking without
   that panel still reads as a cosine dump.

## Status Quo

`backend/app/search.py`, unchanged since M4.2:

```
query
  → embed_texts([query])            bge-small-en-v1.5, 384-dim
  → parallel:
      $vectorSearch  (pool 30, numCandidates 300)
      $search        (paths: business_name, keywords, specialties,
                      products_services; score-threshold 0.3x top hit)
  → weighted RRF     (0.7 vector / 0.3 keyword, k=60)
  → cross-encoder rerank top-20     ms-marco-MiniLM-L-6-v2
  → top-N
```

This is a competent retrieval stack. The reviewer is not attacking it. Keep it.

**The measurement gap is the real finding.** `backend/scripts/eval_dataset.py`
holds 30 labeled queries across 6 categories. Every one of them names the
service, just in other words:

| id | query | why it is easy |
|---|---|---|
| `sem-02` | "looking for a place to stay overnight during my business trip" | *stay overnight* sits adjacent to *hotel* |
| `syn-01` | "computer hacking defense and security auditing firm" | *hacking defense* is one hop from *cybersecurity* |
| `edge-05` | long paragraph naming SOC, penetration testing, ISO27001 | literal terms, verbose only |

**Zero symptom-only queries.** The benchmark that gave this project its
credibility never tested the class of query the reviewer cares about. That is
the honest version of the diagnosis, and it is also the fix: build the
benchmark first, then build against it.

## Target User & Narrowest Wedge

**User:** a non-expert business owner who knows their problem and does not know
the industry's name for the solution. They type symptoms, not SIC codes.

**Wedge:** a query-understanding stage that classifies the described problem
into the corpus's own 40 sub-categories, plus a benchmark that proves it moved
the number. Everything else on this page is amplification of that wedge.

## Constraints

- LLM API at query time is permitted (decided this session, reverses premise 4
  of `docs/MEETING_STUDY_BRIEF.md`). Free tier is fine: Groq or Gemini Flash.
- 2 to 3 days of work.
- Extension, not rewrite. `/api/search` contract may gain fields, must not

- Corpus is 120 businesses, exactly 3 per sub-category, 40 sub-categories.
- Demo must not hard-fail when the network or the LLM key is unavailable.

## Premises

Agreed this session:

1. **This is a query-understanding gap, not a retrieval gap.** Add a stage in
   front; do not touch the fusion or the reranker.
2. **The LLM is constrained to the corpus's live taxonomy, never free-generating
   service names.** The allow-list already exists:
   `filters.get_filter_allowlist()["sub_category"]` returns the live distinct
   values and is already cache-invalidated on registration. The LLM performs
   *classification into a known label set*, which is defensible, testable, and
   answers "how does this work at scale" (the label set grows with the corpus;
   the mechanism does not change). Free generation invents categories that do
   not exist and drifts retrieval into noise.
3. **The cross-encoder reranks against the ORIGINAL query, never the rewrite.**
   Retrieval widens on the interpretation; ranking judges against what the human
   actually typed. If the rewrite fed both, a wrong interpretation would become
   unfalsifiable and errors would compound silently.
4. **It does not count unless it is measured.** New `situational` eval category,
   before/after numbers, worsened cases reported.
5. **It does not count unless it is visible.** The inferred need renders in the UI.
6. **Latency is handled, not ignored.** Cache, timeout, graceful degradation to
   today's exact behavior.

## Approaches Considered

### Approach A: Query-side intent extraction only
LLM stage in front of retrieval; corpus untouched; no re-embed.
Effort S. Rejected as the whole answer: puts a network call on every search
with no offline path, and a single wrong classification loses the query
entirely. Retained as **a component** of the recommendation.

### Approach B: Document-side problem-space enrichment only
One offline LLM pass writing "problems we solve" in customer language into each
of the 120 records; fold into embedding text; re-embed. Zero query-time LLM.
Effort M. Rejected as the whole answer: cannot extract a constraint from
"suspicious emails, and we're in Pune", and produces no visible reasoning
artifact, so it does not answer the second half of the reviewer's complaint.
Retained as **a component** of the recommendation.

### Approach D: C plus an LLM reasoning reranker
Everything in C, plus a batched LLM call that scores the top candidates and
writes a one-line justification per result. Strongest demo. Rejected for this
round on time: adds 1 to 2 seconds of latency needing streaming or optimistic
render, and a 4-way ablation to justify it. Listed in Open Questions as the
next increment.

## Recommended Approach

**C — close the gap from both ends, prove it, and show it.**

Four independently shippable pieces.

### C1. Query-side intent extraction — `backend/app/intent.py` (new)

```python
@dataclass(frozen=True)
class QueryIntent:
    underlying_need: str            # "phishing protection and employee security awareness"
    service_categories: list[str]   # STRICT subset of live sub_category allow-list
    excluded_categories: list[str]  # STRICT subset too; what the user ruled OUT
    exclusion_terms: list[str]      # free-text negations that map to no category
    expanded_query: str             # service-vocabulary rewrite, retrieval only
    suggested_filters: dict[str, str]   # city/industry/state pulled from the sentence
    source: str                     # "llm" | "cache" | "fallback"
    confidence: float
```

**Why `excluded_categories` exists, and why it cannot live in the vector.**
Embeddings are bad at negation. `"not a WhatsApp bot company"` embeds close to
`"WhatsApp bot company"` because the content words dominate and the negation is
a single weak token. The cross-encoder helps marginally and not enough. So
negation is extracted symbolically by the LLM and enforced symbolically after
retrieval (C2), never handed to the vector space and hoped for.

Worked example: `"I don't want WhatsApp bot companies"`. A naive intent layer
classifies this as `service_categories: ["Software"]` and makes the result
strictly worse than no intent layer at all. The correct extraction is
`service_categories: []`, `excluded_categories: ["Software"]` (or whichever
sub-category covers chat automation in the live taxonomy).

**Prompt inputs:** the user query, plus the live allow-lists for
`sub_category`, `city`, `industry`, `state` read from
`filters.get_filter_allowlist()`. No new infrastructure; that function already
exists and already invalidates on registration.

**Prompt contract:** return JSON only. `service_categories` and
`excluded_categories` MUST be values from the supplied list; return `[]` if
nothing fits. Do not invent a category. Do not return a filter value that is not
in the supplied list. If the user negates something ("not", "don't want",
"anything but", "other than", "except"), it belongs in `excluded_categories` or
`exclusion_terms`, never in `service_categories`.

**Post-validation (belt and braces, do not trust the model):** drop any
`service_categories` or `excluded_categories` entry not in the allow-list; drop
any `suggested_filters` value not in the allow-list. A hallucinated label never
reaches retrieval. Additionally, if a category appears in both lists, drop it
from both and log it: that is a confused extraction and acting on either half
is worse than acting on neither.

**Model:** Groq `llama-3.3-70b-versatile` or Gemini `2.0-flash`, JSON mode,
`temperature=0`. Both have usable free tiers. Target 300 to 600ms.

**Cache:** in-process dict keyed on `(normalized_query, allowlist_version)`.
Bump `allowlist_version` inside `filters.invalidate_filter_cache()` so a new
registration cannot serve a stale taxonomy. A cached hit is roughly 0ms, which
is what makes a live demo feel instant on repeat queries.

**Failure path:** 2s timeout, any exception, or missing API key returns
`QueryIntent(underlying_need=query, service_categories=[], expanded_query=query,
suggested_filters={}, source="fallback")`. That reproduces today's behavior
byte for byte. Same posture as the existing reranker try/except in
`search.py` — the quality layer degrades, the search does not 503. Expose it on
a new `/health/intent` endpoint alongside `/health/model` and
`/health/reranker`.

### C2. Three-arm retrieval — modify `backend/app/search.py`

Do **not** replace the original query's vector arm with the rewritten one. If
the interpretation is wrong, that would throw away the only honest signal.
Run both and let fusion arbitrate.

```
query
  ├─ LLM intent extraction (cached, 2s timeout)
  │
  ├─ arm 1: $vectorSearch on embed(original query)           weight 0.5
  └─ arm 2: $vectorSearch on embed(expanded_query)           weight 0.5

  (keyword arm: OFF by default in rev 3. Kept behind a config flag
   so rung E of the eval ladder can readmit it if the numbers say so.)
       ↓
  weighted RRF, k=60
       ↓
  cross-encoder rerank top-20 against the ORIGINAL query
       ↓
  apply exclusions (symbolic, post-rank)
       ↓
  top-N + intent object
```

**Exclusion enforcement is the last stage, after ranking, and it is a hard
filter.** Drop any candidate whose `sub_category` is in
`intent.excluded_categories`, or whose `symptom_phrases` / `keywords` match an
`exclusion_terms` entry. Placing it after reranking rather than before retrieval
means an over-eager exclusion cannot silently starve the candidate pool, and the
UI can honestly report "3 results hidden because you excluded WhatsApp bots"
with an undo. Never fold exclusions into the embedded query: see C1 on why the
vector space cannot represent negation.

**Keep both vector arms. This is the point of the design.** Arm 2 alone would
mean the LLM's interpretation is the only signal reaching retrieval, so a single
misread query has no recovery path. Arm 1 is the safety net that makes the
intent layer safe to be wrong. When the interpretation is good, both arms agree
and RRF reinforces the result; when it is bad, arm 1 holds the line. Any
proposal to embed only the rewritten query is asking the LLM to decide the
outcome unilaterally, which is the exact failure mode this structure exists to
prevent.

Refactor `_reciprocal_rank_fusion(vector_results, keyword_results, ...)` to take
`list[tuple[str, float, list[dict]]]` (name, weight, results). This generalizes
the existing two-arm signature, keeps `matched_via` working (now a set of arm
names), and is what makes the ablation in C4 possible without duplicating the
function — the same override pattern already used for the pre-M4.1.1 comparison.

When `source == "fallback"`, arm 2 is skipped and weights collapse to today's
0.7/0.3. Identical behavior, no special-casing downstream.

**Starting weights are a reasoned guess, not grid-searched.** Say that in the
code comment, the same way the existing `RRF_WEIGHT_VECTOR` comment does, and
validate them by re-running the eval. Do not claim they are optimal.

**The keyword arm is off by default, and this is a deliberate reversal.** Rev 1
kept it at weight 0.2 on the reasoning that the `kw-*` eval category needs it.
Rev 3 removes it from the default path because assuming it is necessary is
exactly the posture this project is supposed to reject, and because your own
M4.1 comment in `search.py` already records that keyword search "never
contributed a unique win anywhere in the golden set" while "repeatedly diluting
otherwise-correct vector rankings." Keep the code path behind
`KEYWORD_ARM_ENABLED` (same env-toggle pattern as `RERANK_ENABLED`) so rung E
can readmit it on evidence rather than on argument.

**The one concrete cost, stated plainly so it is not a surprise later.**
`business_name` currently sits in `SEARCH_TEXT_PATHS` for exact-name lookup, and
that is what PR #2 (`3657ac5 fix: make registered businesses findable by exact name`) existed to fix.
`business_name` is also in `build_embedding_text()`, so vector-only degrades
that lookup rather than breaking it. Watch it in the eval. If exact-name lookup
regresses, the mitigation is **not** to restore general BM25 over descriptions;
it is a narrow `$search` path scoped to `business_name` alone. That is an exact-
lookup feature, not the "basic keyword search" ranking approach under
criticism, and it should be argued as such.

**Suggested filters are surfaced, never silently applied.** Pre-fill the filter
chip in the UI, marked removable, and only when the user has not already set
that field. Silently applying an inferred `city` can zero out a result set and
the user would have no idea why.

### C3. Category-level enrichment — `backend/scripts/enrich_businesses.py` (new)

**Rev 4 reduces this from 120 calls to 40, and commits the output.**

The three businesses in each sub-category carry byte-identical `Products/Services`,
`Keywords` and `Specialties`. Enriching per-business would make 120 calls to
produce 40 distinct payloads, and any per-business variation the model introduced
would inject noise between three businesses the ground truth asserts are equally
relevant. So enrichment is **keyed on `sub_category`**, and it is a category-level
gloss, not per-business content. Say that plainly in the meeting; it is a stronger
answer than pretending 120 documents exist.

Per sub-category the LLM writes:

- `problems_solved` — 2 to 3 sentences in customer symptom language.
- `symptom_phrases` — 5 to 8 short phrases a real person would type, stored as a
  **delimited string, not a list**. `build_embedding_text()` does
  `" ".join(p.strip() for p in parts)`; a list has no `.strip()` and would raise
  `AttributeError` on every embed and every rerank.

**The output is committed: `backend/data/enrichment.json`, keyed by sub-category.**
`seed.py` reads it. `--regenerate` is the opt-in path that calls the LLM. This one
decision fixes four separate problems at once:

- a grader with no LLM key still gets the enriched corpus;
- `seed.py`'s `delete_many({})` at line 109 no longer silently destroys enrichment;
- the script becomes trivially resumable and idempotent;
- rungs C and D become reproducible by someone who is not you.

It also turns enrichment from an unauditable side effect into a reviewable diff,
which is itself a good artifact to hand a grader.

**Wiring — rev 3's list was incomplete:**
- `embeddings.build_embedding_text()` gains both fields.
- `search.SEARCH_TEXT_PATHS` gains **`symptom_phrases` only** (see below).
- **`search._PROJECT_STAGE` gains both fields.** Rev 3 missed this and it is a
  silent-failure bug: `reranker.rerank_candidates` calls `build_embedding_text(doc)`
  on the *projected* document. Today `RESULT_FIELDS` happens to cover every field
  that function reads. After C3 it would not, so the reranker would score truncated
  documents and enrichment would be thrown away at rank time — confounding rung C
  against rung D. Keep `_PROJECT_STAGE` a separate dict from `RESULT_FIELDS` so the
  new fields do not leak into the API response.
- Add a unit assertion: the field set `build_embedding_text` reads must be a subset
  of `_PROJECT_STAGE`.
- `scripts/atlas_indexes/search_index.json` is `dynamic: false`, so `symptom_phrases`
  needs an explicit `{"type": "string"}` entry.
- Re-run `scripts/reembed_businesses.py`.
- Registration enrichment moves **out of the request path**. Mark new documents
  `enrichment_status: "pending"` and enrich in a batch. Rev 3's synchronous version
  put a 1-3s LLM call in front of the embed in a form submit, and a silent
  insert-without-enrichment leaves the corpus heterogeneous with no flag and no
  retry, making rung C depend on how many enrichments happened to succeed.

**Why `problems_solved` stays out of the keyword paths.** A verbose LLM-written
paragraph is exactly the text that produced the `"business trip"` / `"business
insurance"` collision documented in M4.1.1. Long prose goes to the embedding, where
it helps; short discriminative phrases go to Lucene, where boilerplate hurts.

**Enrichment output is untrusted input.** `business_description` and
`products_services` are attacker-controlled (5000 chars, unauthenticated endpoint).
An injected instruction can make the model write `symptom_phrases` that rank a
business for every query — a self-serve ranking hijack. Validate generated phrases
against a count and length cap, and reject any phrase sharing no term with that
sub-category's own `keywords`. The forbidden-filler-word check from rev 3 is a
quality guard, not a security one, and its regeneration loop needs a retry cap of 3
or it is unbounded.

### The ablation ladder

**One variable per rung.** Committing intent fixtures (see Reproducibility below)
makes each rung deterministic and free to re-run, which is what keeps a
multi-rung ladder affordable.

| rung | config | intent | enrich | keyword | rerank input | isolates |
|---|---|---|---|---|---|---|
| **A** | current system, as shipped | off | off | **on** | original | honest starting point |
| **A'** | A minus the keyword arm | off | off | off | original | what keyword retrieval contributes |
| **B** | A' plus query understanding | **on** | off | off | original | the intent layer alone |
| **B2** | B, reranking on `underlying_need` | on | off | off | **need** | **whether the reranker fights the intent layer** |
| **C** | B plus enriched corpus | on | **on** | off | best of B/B2 | enrichment alone |
| **D** | C minus the reranker | on | on | off | **none** | whether the cross-encoder still earns ~405ms |

**Rung B2 is the most important new rung and it did not exist in rev 3.** Three
independent reviewers reached the same conclusion: `ms-marco-MiniLM-L-6-v2` is a
22M-parameter model with the same world-knowledge ceiling as BGE. If it cannot
bridge "suspicious emails" to "SOC", then reranking against the original query
demotes the exact result the intent arm just promoted, and the intent layer's
gain is eaten in the final stage. B vs B2 vs D measures that directly.

**Rung E (readmitting keyword on top of the new system) is cut.** With the metric
fixed and rung A' answering the keyword question on today's system with one
variable moved, E adds a rung and answers nothing new.

**Metrics, in reporting order:**

1. **success@3** — did all 3 correct businesses land in the top 3. Real headroom,
   and it matches how the reviewer stated the goal.
2. **recall@3**.
3. **exclusion_violations@5** — count of excluded-category businesses appearing in
   the top 5. Boolean-style assertion for the `negation` category.
4. **P@5 with its ceiling printed beside it**, as a regression tripwire only.

`precision_at_k` currently returns `0.0` for zero-relevant queries and is averaged
in, while `recall_at_k` returns `None` and is excluded. Fix that asymmetry before
the baseline is committed, or the adversarial cases are pinned at 0.0 whether they
pass or fail.

Report per category, always. A single overall number hides the tradeoff where
`situational` improves while `keyword` regresses. Adding ~15 queries also makes
the overall row incomparable to `report_20260720_200803.md`, so report the frozen
original-30 subset alongside the full set.

**Methodological rule, and this is the one that earns respect: freeze the 10
situational queries and record baseline numbers BEFORE writing any enrichment
text.** If you author enrichment first and eval queries second, you are grading
your own homework and a good reviewer will spot it in one question.

**Report what got worse.** The existing `eval_reports/` and the docstring in
`search.py` are unusually honest — *"Confirmed NOT a complete fix, not oversold
as one"*. That honesty is the most valuable thing in this repo. Keep it. If
`+intent` costs you precision on the `keyword` category (plausible: expansion
adds noise to already-literal queries), publish the number and explain the
tradeoff. Consider skipping intent extraction when the query is short and
already matches a category name — but only if the eval says so.

### C5. Make it visible — `SearchPage.tsx`, `schemas.py`, `types/api.ts`

`/api/search` response gains an `intent` object. Additive field, existing
clients unaffected.

Panel above results:

```
You asked:   "My company keeps getting suspicious emails and I want
              someone to make sure our employees don't fall for scams"

I understood you need:
  Phishing protection and employee security awareness training

Searching for:  [Cybersecurity]  [Corporate Training]
Excluding:      [WhatsApp Bots x]
Detected:       [Pune x]
```

Excluded categories render as removable chips exactly like detected filters, and
when exclusions actually removed something, say so under the results: *"3
results hidden because you excluded WhatsApp bots. Show them."* Silently
disappearing results is the fastest way to make a search feel broken, and an
undoable exclusion chip is also the clearest possible demo of the feature.

When `source == "fallback"`, render a quiet line: *"Showing direct match —
query interpretation unavailable."* Never a red error. Degradation should look
deliberate.

This panel is doing more work than it looks like. It is the single artifact
that turns "the ranking happens to be right" into "the system understood me,"
and it is what the reviewer will screenshot.

### Latency budget

| stage | cold | cached |
|---|---|---|
| intent LLM | 300-600ms | ~0ms |
| embed query x2 | ~15ms | ~15ms |
| Atlas (3 arms, parallel) | 50-100ms | 50-100ms |
| cross-encoder, 20 docs | ~405ms (repo-measured) | ~405ms |
| **total** | **~0.9-1.2s** | **~0.5-0.6s** |

Optimization worth naming in the meeting: fire arm 1 (original-query vector) in
the existing `ThreadPoolExecutor` **concurrently with** the LLM call, then add
arm 2 when intent lands. The LLM latency overlaps retrieval instead of stacking
on top of it. `search.py` already uses `ThreadPoolExecutor`, so this is a
scheduling change, not new machinery.

## Open Questions

1. **Which provider.** Groq (fastest, generous free tier, occasional capacity
   errors) vs Gemini Flash (more reliable, slightly slower). Recommend Groq,
   with the fallback path making capacity errors a non-event.
2. **Multi-intent handling.** Your `multi_intent` category already exists.
   Should the intent stage return multiple `service_categories` and fan out one
